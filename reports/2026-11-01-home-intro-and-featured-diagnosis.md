## 已证实的布局机制

1. `src/components/content/home-featured-posts.css`：Grid 两列为 `1.8fr / 1fr`，列间距 28px、行间距 22px；主卡 `grid-row: span 2`。当容器宽 1140px 时，两列实际约 714.84 / 397.14px。
2. `HomeFeaturedPosts.tsx` 把各篇 `post.coverSettings` 原样交给 `CoverFrame`，没有主图/次级位置的独立比例。`cover/contracts.ts` 默认是 `original + contain`，比例枚举没有 3:2。
3. `.article-card-visual.has-cover` 取消占位框的 `aspect-ratio` 和主图 `min-height`，并设为 `flex: none`（计算值 `0 0 auto`）。原图模式下图片的自然比例决定高度；固定比例模式由 `--cover-ratio` 决定。`contain` 补边、`cover` 裁切、焦点与缩放决定框内画面，不改变预设框的高度。
4. Grid 默认 stretch 会让主卡不可见外框跨满两行，但其图片与文字仍按自身内容高度排列，不会自动填满。因此外框对齐不等于图片/文字的可见底部对齐。标题行数、字号、日期行、主卡摘要、文字 padding 还会分别增加实际内容高度。

## 真实本地测量

1440×1100 视口，1140px 容器，三张合成封面依次为 16:9 / 3:2 / 16:9，全部 `original + contain`。首次真实 API 上传/发布到临时数据库后读取页面：

| 元素 | 主卡 | 右上 | 右下 |
| --- | ---: | ---: | ---: |
| 封面宽×高 px | 714.84×402.09 | 397.14×264.75 | 397.14×223.39 |
| 文字区域高度 px | 111.19 | 63.59 | 63.59 |
| 标题高度 px | 45 | 27 | 27 |
| 卡片外框底部 y | 849.72 | 540.73 | 849.72 |
| 可见内容底部 y | 725.67 | 540.73 | 849.72 |

两列顶为 y=212.39；Grid 两行 328.34 / 286.98px。主卡外框底部已经等于右列底部，可见内容仍短约 **124.05px**。封面尺寸与截图描述高度吻合，但不能由此确认生产三篇的实际设置一定是 original；固定比例同样可能得到这些尺寸。

仅在本地浏览器临时改 DOM 比例（不保存文章、不修改源码）验证设计目标：主框 3:2、右侧两框 16:9，主封面高 476.56px、右封面各高 223.39px；主可见内容底部 800.14、右列 808.36，相差 **8.22px**。右上标题从 1 行增至 4 行（27→108px），右列增高 81px，差距扩大到 **89.22px**，主图及主文字高度不变。

因此混合比例是已证实的贡献因素，文字自然高度及主卡不伸展同样参与；“把比例统一”不能保证“任意内容下整列底部等高”。这不是图片编码尺寸导致的拉伸，也没有证据说明 Grid 的列定位失效。

## 建议，尚未实施

- 若目标是封面观感统一：明确首页按位置采用主 3:2、次级/普通 16:9，以及与文章自定义设置的优先级，再在共享展示层实现；保留原文件、主体焦点及文章页语义，避免批量改文章配置。现有协议没有 3:2，不能只写文档就算完成。
- 若还要求整列可见底部严格等高：需另行确定对齐的是封面底、文字底还是卡片外框，并决定长标题/摘要的完整显示、留白和图片比例之间的取舍。固定两种比例、自然文字高度与任意内容严格等高不能仅靠现有 auto Grid 同时保证。不要未经确认直接拉伸图像或截断文字。
- 线上可读取后，应逐篇核对发布快照的 `coverSettings`、自然尺寸、实际 computed style 及字体/标题行数，验证本地机制是否为该生产实例的实际原因。
