## 问题详情

### B1: 手工迁移与 Drizzle snapshot 分叉，下一次生成重复列迁移

**来源**: 模型与迁移不变量检查  
**关联不变量**: INV-CAND-01  
**文件**: `drizzle/meta/0002_snapshot.json`、`drizzle/meta/_journal.json`、`drizzle/0004_google_session_display_name.sql`、`src/server/db/schema.ts`  
**位置**: snapshot第480–518行；journal第24–32行；0004 SQL第3行；schema第112行  
**严重程度**: P1  
**置信度**: 已确认  
**根因分类**: spec 缺口

**问题描述**：0004手工给google_author_sessions添加display_name，schema也包含该列；最新snapshot仍描述五列。后续db:generate把已执行变更当作新增，再生成同名列操作。

**不变量检查**：规则为已执行迁移与当前模型可继续演进；路径为schema→snapshot diff→新SQL→DB。最小反例：当前四条SQL已执行，schema保持当前内容，运行generate并应用新SQL。实跑生成新的 `0004_*.sql`，内容为 `ALTER TABLE google_author_sessions ADD display_name text;`，SQLite报 `duplicate column name: display_name`。结论：破坏。

**贝叶斯更新**：先验中；元数据差异支持候选，生成和真实SQLite应用将置信度更新为已确认。反证检查读取全部迁移与journal、当前Drizzle配置及schema；现有测试只顺序执行已有SQL，覆盖当前表结构，生成下一条迁移的路径留有空白。

**Spec 对照**：db/README声明schema与可执行迁移；package提供db:generate；手工迁移后的metadata同步步骤缺少明确验收。归类为spec缺口，同时存在已确认的模型漂移。

**影响**：下一次数据库结构迭代或按文档生成迁移时阻断发布；当前已有列和数据仍可使用。

**验证方式**：[migration.log](../audit/architecture-review-validation-20261031.md)，隔离探针 [review-drizzle.mjs](../audit/architecture-review-validation-20261031.md)。最短取证：复制schema/drizzle到临时目录运行generator，再把新增SQL应用到已经执行现有迁移的内存库。

**修复建议**：为手工迁移补齐一致的snapshot和journal，保持既有已部署SQL的历史；同时验证全新库与已有库继续生成/应用。将同步规则写入drizzle README。

### B2: 集成打包白名单遗漏共享协议的新增依赖

**来源**: 跨模块交付依赖检查  
**关联不变量**: INV-SPEC-08  
**文件**: `integrations/scripts/package.mjs`、`src/shared/contracts.ts`  
**位置**: package第21–35行；contracts第4–16行  
**严重程度**: P1  
**置信度**: 已确认  
**根因分类**: 实现过程偏移

**问题描述**：打包脚本只将integrations源码和contracts.ts写入全新stage；contracts已依赖config/limits.ts、schema.ts、public.ts及后续embed注册表。stage在运行Node集成测试时缺少这些本地源码。

**不变量检查**：来源为INSTALL第32–42行的可复现打包约定；路径sourceFiles→stage/source→Node tests→contracts imports。最小反例：按HEAD和脚本清单建立stage，连接现有node_modules，运行stage的集成测试。实际3个测试文件报 `ERR_MODULE_NOT_FOUND: src/modules/config/limits.ts`；权限检查1项通过。结论：破坏。

**贝叶斯更新**：先验中；清单与contracts依赖差异支持候选；原始已提交文件归档后的stage执行确认。反证检查确认node_modules可用、Node24支持当前TS加载、容器与仓库lock一致。失败发生在本地源码解析，后续浏览器/Obsidian/CLI构建阶段尚未到达。

**Spec 对照**：INSTALL约定在完整仓库现有依赖下隔离构建；当前stage白名单停留在contracts自足时的边界。分类：实现过程偏移。

**影响**：当前提交重新交付Chrome/Obsidian/CLI安装包的流程中断；历史已生成安装包的运行情况属于各自版本证据。

**验证方式**：[package.log](../audit/architecture-review-validation-20261031.md)。本次复现精确执行脚本的sourceFiles白名单与stage测试步骤，外层完整package脚本的ZIP阶段保持未触达；第33行会因同一stage错误退出。

**修复建议**：将协议及其依赖作为显式可构建单元，或从源码import图推导完整闭包。集成交付校验应从最终白名单stage执行，并记录完整依赖来源。

### B3: 媒体库 SSR 使用默认条数，API 使用作者配置

**来源**: 配置生效不变量检查  
**关联不变量**: INV-SPEC-05  
**文件**: `src/server/page-data.ts`、`src/server/media/service.ts`、`src/server/api.ts`  
**位置**: page-data第168/243行；media service第192行；api第307–312行  
**严重程度**: P1  
**置信度**: 已确认  
**根因分类**: 实现过程偏移

**问题描述**：loadStudioPageData和loadMediaPageData调用listMedia时省略limit，触发DEFAULT_CONFIG.media.listLimit=100；GET /api/media显式传入requestConfig中的作者值。

**不变量检查**：config README约定作者配置下次请求生效，meta第65行定义一次列出的文件数。路径settings→SSR loader→listMedia与settings→API→requestConfig→listMedia。最小反例配置20、媒体25条：实测Studio SSR25、Media SSR25、HTTP20。预期三个入口20。结论：破坏。

**贝叶斯更新**：先验中；遗漏参数和默认参数直接支持，真实SQLite/HTTP调用确认。反证检查确认配置持久化成功，API正确返回20，界面把SSR列表作为初始数据；两次入口共享同一环境和媒体数据。

**Spec 对照**：统一配置使用约定被SSR路径遗漏，分类：实现过程偏移。README关于请求配置的约定仍明确。

**影响**：首屏与刷新/搜索后条数跳变；作者配置大于100时首屏仍只列100条。

**验证方式**：[counterexamples.log](../audit/architecture-review-validation-20261031.md) 的MEDIA_LIMIT_OBSERVED；[探针](../audit/architecture-review-validation-20261031.md)首个用例。

**修复建议**：将媒体查询配置和过滤收敛到一个应用用例，SSR和API共同调用；至少向两个SSR调用显式传入已读取的settings.limits.media.listLimit。补默认值以外的SSR/API一致性断言。

### B4: 保存与阅读两份 href 规则漂移，邮件链接发布后退化为文字

**来源**: 共享规则与消费者检查  
**关联不变量**: INV-SPEC-06  
**文件**: `src/modules/content-check/index.ts`、`src/components/content/BlockReader.tsx`、`src/components/shared/ui.tsx`  
**位置**: content-check第67–72行；BlockReader第71–79行；ui第247–260行  
**严重程度**: P1  
**置信度**: 已确认  
**根因分类**: 实现过程偏移

**问题描述**：isAllowedLink明确接受href=mailto；服务端保存/发布复用该规则。阅读端使用safeUrl，其协议白名单仅含http/https，所以mailto分支只保留链接文字。

**不变量检查**：content README声明支持邮件链接，content-check README定义href规则。路径create→validateContent→publish→published.blocks→BlockReader.Inline→safeUrl。最小反例：包含 `mailto:writer@example.com` 的inline link。保存和发布成功，published JSON仍含href，SSR HTML为 `<p><span>Contact author</span></p>`。结论：破坏。

**贝叶斯更新**：先验中；源码两份白名单支持，经过真实SQLite保存/发布及React静态渲染确认。反证检查确认blocks结构通过schema、内容成功发布；媒体URL、导航URL和下载URL有各自sink语义，需要保留具名场景约束。

**Spec 对照**：写入端和阅读端对同一个href给出不同语义。分类：实现过程偏移；结构根因关联架构A5。

**影响**：作者接受并发布的邮件联系链接在阅读页失去点击能力。

**验证方式**：[counterexamples.log](../audit/architecture-review-validation-20261031.md) 的MAILTO_OBSERVED；[探针](../audit/architecture-review-validation-20261031.md)第二个用例。

**修复建议**：建立纯共享href policy供保存与阅读使用；为媒体、导航、下载单独提供具名策略。回归需要跨越保存→发布→渲染完整链。

### B5: 常驻工作台消费资源异常后丢弃结构化错误证据

**来源**: 失败路径与可观测性约定
